# P3 independent cross-judge

Use **B as the implementation base**, graft A's acquisition fencing and cleanup semantics, and retain C's explicit stale-observation protection without its reservation table or reducer framework. B provides the clearest seam: synchronous SQLite transactions own durable truth; the asynchronous pump owns disposable execution handles. This verdict evaluates the candidates as written, before these corrections.

A wins the raw safety rubric. This is a base-plus-grafts recommendation, not acceptance of B unchanged.

## Required grafts and decisions

1. **Keep three durable tables.** Commands contain immutable canonical input and result; runs contain current lifecycle and frozen nonsecret configuration; resources contain intent, ownership and unresolved obligations. SQL transactions enforce reservation rules. A fourth slot/reservation table creates another representation to keep consistent when the single writer can calculate occupancy from these tables. Define device occupancy as a distinct union of executing/stopping devices and unresolved-resource devices, avoiding duplicate counts.
2. **Reserve the entire requested page demand atomically at dispatch.** Default policy is two executing devices and four total pages. Freeze `settings.pageCount` and settings revision at command acceptance, and record a durable refusal when demand exceeds capacity. A's individually acquired page obligations need this correction: incremental reservation can strand two partially provisioned runs. Queued runs reserve device identity but consume no execution/page slots. Starting/running/stopping runs and unresolved acquisition/release obligations retain their capacity.
3. **Never drop a successful late acquisition.** Persist a stable operation ID, owner marker and discoverable locator before any effect. Cancellation prevents subsequent execution but does not discard acquisition results; record and clean them even after the run entered stopping. State-conditional updates must distinguish suppressing stale execution success from losing a cleanup obligation.
4. **Absence must be final.** Adopt A's `present | absent-final | unknown` reconciliation contract. A negative lookup is insufficient while delayed external creation remains possible. The durable filesystem driver must account for outstanding local acquisition work; an independent fault service must fence/tombstone the operation before declaring absence. Unknown retains full capacity. Resolve obligations only after verified deletion/detachment. Partial or mismatched ownership markers are unknown, not deletion authority.
5. **Cleanup failure stays stopping.** Remove B's transition to failed/CLEANUP_REQUIRED while cleanup remains unresolved. Publish safe failure information and retain the pending terminal target plus obligations. Normal completion, cancellation or failure becomes terminal only after cleanup is proved. On restart, interrupt every previous queued/starting/running/stopping run; unresolved resources remain visible and blocking independently of the interrupted terminal state. Recovery can reconcile cleanup but never replay execution.
6. **Keep five public work operations.** Add `work.getSnapshot()` alongside start/cancel/getCommand/subscribe for existing UI and packaged-test consumers. It returns the same complete authoritative snapshot as subscription, with epoch/revision; it is not a second state model. A main-owned connection generation gates both responses and events. Once unavailable, stale snapshots cannot restore readiness. Subscription registration plus initial state must not lose transitions.
7. **Keep control parameters private.** The controlled duration is a fixed worker policy; no renderer duration/fault options, arbitrary production environment injection, browser credentials, material claims or business-history writes. Public snapshots explicitly identify controlled execution. Tests can inject drivers through private composition.
8. **Use the live-child exit fence.** Persist/flushed sidecar authorization before initialize and start heartbeat/watchdog protection before opening SQLite. Initialization expires without authorization. A stale recorded PID can only block startup or be proved absent; never kill it. Prefer the actual live child handle for termination. If that cannot force termination, an OS kill may target only the current child whose identity is still owned and tied to the live handle; always await actual exit afterward. Unknown ownership or unconfirmed exit blocks replacement. No kill return, shutdown ACK or SQLite lock proves exit. Budget ten seconds cooperative plus five seconds force/confirmation. Forced stop is never reported clean.
9. **Treat migration correctness as a prerequisite.** Validate the known version's schema and checksum prefix, back up through the exclusively owned connection including committed WAL, verify every existing table/ledger, and apply pending SQL only. Preserve v2 settings revision/reference, material status 1 and business rows; never replay migration 002 or its resets.

## How the resulting design works

The renderer retains a command ID and sends a business device ID. One SQLite transaction either returns the stored command result or records the new immutable receipt and queued run with frozen settings. The pump asks the repository to admit the oldest eligible run; that transaction reserves all required capacity and writes acquisition intent before the driver touches the filesystem. The driver returns observations, and conditional repository transitions decide whether execution may continue or cleanup is required. Cancellation records durable stop intent first and then aborts the disposable execution handle. Cleanup proof releases capacity and allows normal terminal state. After a process loss, a replacement is authorized only after the previous process is confirmed absent; it interrupts old work and reconciles obligations without executing that work again.

## Verification gates before declaring P3 complete

- Migration from a populated v2 WAL database preserves all rows, settings/reference and ledger; injected migration failure and checksum drift fail safely. Keep P2 CRUD and credential checks.
- Response loss and replay across settings changes/restarts preserve exact start/cancel results, including refusals; conflicting inputs never create work.
- Assert actual external overlap at the two-device/four-page limits, oversized demand rejection, full-demand admission, queued cancellation, and device mutation refusal for active or unresolved work.
- Kill after durable intent and after external creation before result persistence. Observe surviving filesystem effects from outside the worker; recovery interrupts every nonterminal state, cleans owned resources and never increments execution again. Borrowed resources survive.
- A separate controlled service proves cancellation with a late successful acquisition and delayed creation after a transient absence. It must demonstrate fencing before capacity release. Cleanup refusal stays stopping and blocks admission until resolved.
- Portable hanging acquire/execute/cleanup cases prove the shutdown budget and actual exit confirmation. Host death, pre-initialize death, heartbeat expiry, stale live PID and unrelated sentinel process cases prove takeover safety without real browsers.
- Snapshot tests preserve all active/unresolved items beyond terminal history limits and reject stale responses after unavailable. Ordinary fused packaged launch proves queue, cancel, persistence and cleanup. Real development source rebuild proves replacement follows successful predecessor exit; failed build/close cannot start a competing writer.

Scope stops after P3 scheduling/recovery acceptance. No P4 driver integration or real material consumption. The parent agent/model family cannot be established from these candidate artifacts; this verdict makes no claim about it.
