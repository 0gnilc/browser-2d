## 本次补齐的工程缺陷

旧库中的 `device.count` 和 `device.status` 可保存 SQLite 64 位整数。原入口只检查其存储类型，超出 JavaScript 安全整数范围时仍迁移到 v4，随后公共设备查询抛出 ZodError。现有数值边界表已补入这两列，打开数据库时即拒绝不支持的值。新增 10 项实际数据库用例覆盖正负首个越界值、SQLite 极值和合法边界。拒绝后源文件字节、版本和记录保持不变；合法值迁移后及再次打开仍可经公共仓储读取。没有改写既有 SQL 迁移。

Chrome 清理原先在删除用户目录之前写入 `released`，并吞掉删除异常。删除失败现返回 `CLEANUP_FAILED`，资源义务和容量继续保留。持久化停止证明先于目录删除，删除完成后才写入 `released`。中断或部分删除保留证明，重启后可继续清理，不依赖已被删除的调试发现文件。真实数据库、调度服务和 Chrome 配合文件系统边界故障验证这些行为。

原生检查进一步发现，主浏览器退出后仍有 Helper 运行。内核事件记录了 Node 删除目录成功、孤儿 Helper 重建同一路径、测试最后清理再次删除目录的完整顺序。因此，仅观察主 PID 或测试最后没有文件，均不足以证明产品清理完成。当前 POSIX 自有 Chrome 在独立会话和进程组中启动，组标识在 spawned 检查点之前持久化。确认整组已消失后才删除用户目录、释放容量。存储中的组标识只允许信号零查询，不允许对它发送终止信号；现有 CDP 所有权验证和保留的活子进程句柄仍是停止主浏览器的权限来源。

状态 JSON 使用版本化证明，区分未启动、POSIX 组消失和 Windows 主子进程退出。Windows 保留原生关闭路径及真实运行回归，不把子进程退出描述为 POSIX 组证明或通用 Job Object 容纳保证。旧的未完成 attempted、attached、stopped 记录缺少新证明时保持可见的不确定状态；旧 prepared 可安全清理，历史 released 不补造证明。既有 SQL 迁移文件保持原字节。

持有辅助进程的真实 Chrome 用例验证了主进程退出后的容量保留、数据库重开、新驱动恢复、取消、辅助进程晚写和最终清理。原生 ARM 成品还复现了进程组查询暂时返回 `EPERM`、随后恢复为 `ESRCH`。最终等待函数现会在原有截止时间内继续只读观察不确定状态；只有 `ESRCH` 能产生停止证明。25ms 观察间隔、7 秒清理上限、服务重试次数和桌面关闭预算均未增加。负面对照证明，提前结束等待以及把 `EPERM` 当成空组都会让回归失败。

## 本次补齐的验收入口

`pnpm verify:formats -- --target=<目标>` 验证当前干净提交构建的 ZIP 或 AppImage。它先检查源提交、锁文件和完整产物清单，随后运行同一份文件两次，再复核哈希。macOS 从 ZIP 解压出的应用运行。Linux 直接 FUSE 启动原 AppImage，实际 worker 路径必须位于挂载目录。静态 ASAR 和 fuses 仍检查其解包内容，不把解包可运行代替 FUSE 运行。该命令现由正常 native CI 执行，不再依赖硬编码旧 Actions run 的诊断工作流。

新增开发入口场景实际启动 `dev:ui` 和 `dev:worker` 对应脚本。前者使用独立 Chrome 验证预览提示、业务及工作不可用、无特权全局，并确认服务退出。后者两次使用同一临时数据库启动，核对真实 worker 所有权记录、零窗口调试目标、正常关闭及进程消失。第一次关闭全部进程后经业务仓储写入唯一合成设备，第二次启动后核对完整记录及数据库字节。删除数据库的负面对照会因记录缺失而失败。原有 HMR 和源码重启场景继续执行。

伪造浏览器发现文件的回归也已补强。真实 spawned 见证使新驱动实际进入 CDP 所有权检查，测试确认发送了 `Browser.getBrowserCommandLine` 并保留无关测试浏览器及资源义务。临时绕过验证的负面对照会因该浏览器被关闭而失败。测试结束恢复发现文件，再清理自有浏览器。

## 未定位的 Windows 可靠性观察

最终源的首轮 Windows 成品检查曾在第三个 Chrome 的关闭验证页面就绪前超时。前面的数据库、四页面并发、完成及取消已成功，第三次获取仍为 starting。上层日志把验证流程错误归到初始化失败，实际报告说明是等待两页面超时。

随后相同产品提交的完整 Windows 原生任务通过，另一个 [低干扰对照](https://github.com/0gnilc/browser-2d/actions/runs/41217717290)完成 20 次应用启动、60 次 Chrome 获取，没有触发五秒未完成诊断。深层原因未定位，没有声称这次超时已修复。[Issue #8](https://github.com/0gnilc/browser-2d/issues/8) 保留该工程可靠性观察，与签名分发缺口分开。首轮 Intel 的失败为 dmgbuild 卸载临时镜像时 `Resource busy`，同一提交重跑通过，原日志仍保留。

## 阶段结论

P0 至 P5 的当前约定受控流程均有通过结果。P6 工程与四目标预览闭环通过，正式分发仍未完成。上述 Windows 单次未定位超时不被改写成已修复，也不混入用户延期的正式发布资源条件。

1. Windows Authenticode、macOS Developer ID 签名、公证及最终签名产物的重新验收。
